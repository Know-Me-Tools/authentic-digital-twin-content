## The session that started this

_— Travis James._

Four repositories. One system.

`prometheus-uar` is the agent runtime. `flint-gate` is the API gateway. `prometheus-identity` handles auth and credentials. `flint-pmpo` orchestrates the lot. No meaningful change touches fewer than two of them.

I moved off VSCode about eight months ago. The Rust-native performance was obvious from the first session — no Electron tax, no extension host gnawing through 200MB before I'd opened a file. ACP was the deciding factor. One open protocol that connects Claude Code, Codex, and Gemini CLI to the same editor — without a bespoke per-vendor extension — is the first structural improvement the agentic-IDE space has produced in years.

Then I asked an agent to propagate a trait change across the runtime and the gateway. It started searching. It found `src/handler.rs` in two different directories and had no machine-readable way to know which codebase it was operating in. I explained the project structure. The session ended. The next one started cold, with no memory of that explanation.

The agent isn't dumb. The context it was handed is structurally incomplete. That's not a model problem. It's a workspace identity problem — and naming it took longer than fixing it.

## Why Zed, and what ACP actually changed

_— Travis ← AI: Anthropic Claude Opus 4.7 via Claude Code._

A few numbers first, because in this space the numbers do the arguing.

Zed's idle memory footprint with a project open has been benchmarked at roughly 222 MB. VSCode under the same conditions sits around 3,549 MB — a 16× gap. Startup runs under one second for Zed versus two to five for VSCode under typical extension load. Edit latency measures at approximately 58 ms versus 97 ms.

These are not impressions. An agentic session iterating on a cross-service refactor lives inside the editor for hours. A 16× memory gap isn't a laptop-fan problem. It's CPU time and thermal headroom that could be running analysis.

The more important advance is the Agent Client Protocol — ACP. It's an open JSON-RPC standard that decouples AI agents from editors the way LSP decoupled language intelligence from IDEs. An ACP-connected agent runs as a separate process, communicates with the editor over stdio, and is therefore portable. Zed is the reference implementation. JetBrains announced ACP integration in early 2026. Claude Code, Codex, and Gemini CLI all speak it.

The LSP analogy holds precisely. Before LSP, every editor maintained its own Go compiler integration, its own Python type checker, its own Rust analyzer. After LSP, you implement the protocol once and every editor inherits it. Before ACP, each AI coding agent needed a bespoke plugin per IDE. After ACP, you implement the protocol once and every compatible editor inherits the agent.

That's a real architectural advance. What ACP deliberately left out of scope — and what nobody else has filled in — is what the agent is told about the workspace it's operating in.

## Not a missing feature. A missing identity layer.

_— Travis James._

The framing I see in every Zed thread on this — *"Zed is missing the workspace feature"* — is wrong. Or more precisely, it's incomplete in the way that gets a problem fixed at the wrong layer.

Zed has a workspace feature. It's called "Add Folder to Project." You open UAR, add Flint Gate, add Identity, and Zed merges the three into one project tree. From a human's perspective, this is fine. You can open files. You can search. You can run tasks. The recent patches that improve this on Zed's side smooth out edge cases — they don't change the architecture.

From an agent's perspective, the same merge produces one flat namespace. The agent sees `/Users/me/Projects/prometheus-uar/src/handler.rs` and `/Users/me/Projects/flint-gate/src/handler.rs`. Both contain a `Handler` struct. Both implement a shared trait from a common library. The agent has to infer from directory path which service it's looking at, which build contract applies, which environment variables are expected, whether `cargo clippy --workspace` is the agreed quality gate here or some different command per root.

Inference works until it doesn't. It breaks when roots use common naming conventions — which they will, because well-architected systems use consistent terminology. It breaks when you rename a directory. It supplies no machine-readable contract for task execution, so "run the tests" is an instruction the agent resolves by guessing.

Stop. The actual question is not whether Zed has a `.code-workspace` equivalent. The actual question is whether the agent layer has a namespace primitive — and it doesn't. ACP's `initialize` handshake sends `clientInfo` and `agentInfo`. There is no `workspaceInfo`. There is no concept of a named, multi-root workspace anywhere in the protocol. Zed's multi-folder workaround papers over the human-facing side and amplifies the agent-facing side.

Thoughtworks and MIT Technology Review have been calling the category "context engineering" since late 2025 — *a systematic approach to managing how AI systems process context, rather than relying on a loose, vibes-based approach.* The asymmetry is the whole argument: a well-crafted prompt in a poorly engineered context fails; a minimal prompt in a well-engineered context often succeeds. The prompt is tactics. The context is infrastructure.

At the workspace level, context engineering reduces to one requirement. The agent has to know its namespace. Not infer it. Know it.

## What we built

_— Travis ← AI: Anthropic Claude Opus 4.7 via Claude Code._

`zed-workspace` is three Rust crates and roughly 1,800 lines of code. It does not patch Zed, modify ACP, or require root access. It adds one file format, one CLI binary, and one MCP server. It sits beside the existing infrastructure rather than inside it — which is why it shipped in eight weeks instead of becoming a multi-year RFC.

### The manifest: `.zworkspace.toml`

_— Travis James._

The manifest is the source of truth. It declares the workspace name, its root directories and their display names, per-root settings overrides, tasks, debug launch configurations, environment variables. It can live anywhere — in a project directory, in a meta-repo, in `~/.config/zed/workspaces/`. It travels with the team, version-controlled like any other source artifact.

Here's the unabridged manifest for one of our production workspaces.

_— AI verbatim: Anthropic Claude Opus 4.7 via Claude Code._

```toml
[workspace]
name        = "prometheus-core"
description = "UAR · Flint Gate · Identity · Mesh"
icon        = "🔥"

[[roots]]
path = "~/Projects/prometheus-uar"
name = "UAR"

[[roots.tasks]]
label   = "test UAR"
command = "cargo test -p uar"

[[roots]]
path = "~/Projects/flint-gate"
name = "Flint Gate"

[zed]
theme          = "One Dark"
tab_size       = 4
format_on_save = "on"

[[tasks]]
label   = "cargo clippy (all)"
command = "cargo clippy --workspace -- -D warnings"
cwd     = "~/Projects/prometheus-uar"

[env]
RUST_LOG = "debug"

[mcp]
auto_start = true
```

_— Travis James._

Per-root tasks (`[[roots.tasks]]`) scope specific commands to specific services. Workspace tasks (`[[tasks]]`) apply everywhere. Two levels, not seventeen. The manifest is the file we want; everything else is materialization.

### The launcher: `zw`

_— Travis ← AI: Anthropic Claude Opus 4.7 via Claude Code._

`zw open .` does four things in sequence. It resolves all root paths. It deep-merges — never overwrites — `.zed/settings.json`, `tasks.json`, and `debug.json` into every root that exists on disk. It injects a `context_servers` stanza into each root's settings telling Zed to launch `zed-workspace-mcp` over stdio when the session opens. Then it calls `zed --new-window` with all roots as arguments.

Three commands to learn:

_— AI verbatim: Anthropic Claude Opus 4.7 via Claude Code._

```bash
zw init        # scaffold a manifest in the current directory
zw check .     # validate without opening Zed
zw open .      # materialize config and open Zed
```

### The context server: `zed-workspace-mcp`

_— Travis James._

This is the load-bearing piece. An MCP server that Zed spawns over stdio when the session opens — lifecycle managed by Zed, not by a background daemon. Six tools.

_— AI verbatim: Anthropic Claude Opus 4.7 via Claude Code._

| Tool | Function |
|---|---|
| `workspace_info` | Full manifest: name, roots, task count, env keys |
| `list_roots` | Resolved absolute paths for all roots |
| `find_files` | Cross-root glob search, respects `.gitignore` |
| `read_file` | File content, path-jailed to declared roots |
| `grep` | Cross-root regex search, skips binary files |
| `list_tasks` | Workspace task definitions |

_— Travis James._

Two production details worth surfacing because they're the kind of decisions that separate a tool from a proof of concept. The `read_file` tool canonicalizes the requested path and verifies it falls inside a declared root before reading — requests for files outside the workspace return access-denied, not a silent serve of whatever absolute path was supplied. The `grep` tool applies a NUL-byte heuristic to skip binary files and caps maximum file size before reading. Neither is novel. Both are non-negotiable for production tooling.

The server is not Zed-specific. Any MCP-capable client picks it up: Claude Code via `~/.claude/settings.json`, OpenCode via `.opencode/opencode.json`, Cursor and Windsurf and Codex via `.mcp.json`. The included `setup-zed-workspace` skill wires all of them. One install, one manifest, consistent workspace context for every agent in the stack — regardless of which editor they're running in.

The trade-off, because architecture without surfaced trade-offs is sycophancy with a syntax highlighter: this approach depends on the host editor cooperating. Zed cooperates. Cursor, Windsurf, and Codex cooperate via standard MCP. Any editor that ignores MCP context servers gets a no-op until it doesn't. The manifest still works as documentation and as a launcher hint; the agent-side context-injection requires the protocol path.

## A session that made the value obvious

_— Travis James._

Here's the task that made this project worth writing about.

The goal: verify that a new `PolicyScope` enum added to the UAR crate had been propagated consistently to the Flint Gate service. Specifically, every `impl AuthorizationHandler` across both codebases needed to handle the new variant exhaustively. Three minutes of audit if the tooling is right. Forty minutes if it isn't.

**Without `zed-workspace-mcp`:**

The agent opened in a flat multi-root session. It searched for `AuthorizationHandler` and found four implementations across UAR and Flint Gate. When it tried to check exhaustiveness of the match arms on `PolicyScope`, it had to construct paths by reading the directory structure and request content by absolute path. Partway through, it asked: *"Which of these is the gateway-facing implementation?"*

That question contains the entire problem. The answer was sitting in the manifest — Flint Gate is the gateway service; UAR is the runtime. Zero ambiguity, zero inference needed. But the manifest wasn't reachable. The agent had directory names and a guess.

Three clarifying exchanges before the agent had enough context to land a useful answer.

**With `zed-workspace-mcp`:**

The agent called `workspace_info` on session open — the server surfaces this as the recommended first call in its `instructions` field.

_— AI verbatim: Anthropic Claude Opus 4.7 via Claude Code._

```json
{
  "name": "prometheus-core",
  "roots": [
    { "name": "UAR",        "path": "/Users/gqadonis/Projects/prometheus-uar", "exists": true },
    { "name": "Flint Gate", "path": "/Users/gqadonis/Projects/flint-gate",     "exists": true }
  ],
  "task_count": 4,
  "env_keys": ["RUST_LOG"]
}
```

_— Travis James._

Named roots. No ambiguity. Next call:

`grep(pattern: "impl AuthorizationHandler", file_glob: "**/*.rs")`

Results prefixed with named roots:

_— AI verbatim: Anthropic Claude Opus 4.7 via Claude Code._

```
UAR:src/policy/auth.rs:18:        impl AuthorizationHandler for PolicyEngine {
UAR:src/policy/cedar.rs:44:       impl AuthorizationHandler for CedarAdapter {
Flint Gate:src/middleware/auth.rs:31: impl AuthorizationHandler for GatewayAuth {
Flint Gate:src/grpc/auth.rs:67:   impl AuthorizationHandler for GrpcAuthLayer {
```

_— Travis James._

The agent then called `read_file("UAR:src/policy/auth.rs")` and `read_file("Flint Gate:src/middleware/auth.rs")` directly, using the `RootName:relative/path` addressing the server provides. It found the missing variant in the gateway implementation in one pass.

Zero clarifying questions. Zero re-orientation. The same model, the same prompt, a different context layer underneath.

The agent didn't get smarter. It got better equipped. Context that is declared performs differently from context that has to be inferred — and every minute the agent spends asking "where am I?" is a minute it isn't spending on the actual work. That minute compounds across hundreds of sessions.

## From vibe coding to context engineering to workspace identity

_— Travis ← AI: Anthropic Claude Opus 4.7 via Claude Code._

Andrej Karpathy coined "vibe coding" in February 2025. The term named something real — describing intent to an AI and accepting what came back, without necessarily understanding the implementation. For prototypes, for exploration, for the long tail of small tools that previously weren't worth the time to build, it worked. The unlocking was genuine.

The cost showed up within months. Code quality problems. Maintainability problems. Engineers shipping systems they couldn't fully explain. By late 2025, Thoughtworks and MIT Technology Review were describing the next phase as *context engineering* — a systematic discipline of structuring what AI agents know, rather than vibes. The Thoughtworks Technology Radar formulation: *the shift from a loose, vibes-based approach has given way to a systematic approach to managing how AI systems process context.*

The Anthropic 2026 Agentic Coding Trends Report names where this trajectory is heading. Multi-agent systems replace single-agent workflows. Planner, architect, implementer, tester, reviewer — coordinated teams of specialized agents working in parallel across separate context windows. *"Organizations in 2026 will be able to harness multiple agents acting together to handle task complexity that was difficult to imagine just a year ago."*

When five agents work in parallel across a four-repository workspace, workspace identity stops being a developer convenience. It becomes a coordination primitive. Without it, agents operate in the same undifferentiated namespace with no structural boundaries between their domains. You cannot tell the implementer agent *"your domain is UAR, the reviewer's domain is Flint Gate"* — because UAR and Flint Gate have no machine-readable definitions to anchor those assignments to.

Gartner projects 33% of enterprise software will feature agentic AI by 2028. The teams operating at that scale will not be differentiated by model capability. They will be differentiated by how precisely they have structured the context their agents operate in. Workspace identity — the named, versioned, machine-readable definition of which repositories exist, what they are called, and what contracts govern them — is foundational to that structure.

`.zworkspace.toml` is an early answer to that need. It will not be the last.

## What's next

_— Travis James._

The infrastructure for agent portability exists. ACP is stable, adopted, architecturally sound. The infrastructure for workspace identity does not yet exist at the protocol level — there is no workspace primitive in the ACP handshake, no standard for named roots in any editor-agent protocol I've audited.

What we built is a working implementation of that missing layer: a manifest format that names and structures a multi-repository workspace, a launcher that materializes it into Zed's per-root configuration, and an MCP server that hands every ACP-and-MCP-capable agent in the stack a precise, structured understanding of where it is operating.

The honest limit on this work: the manifest format is intentionally minimal. There is more to encode at the workspace identity layer than one team's use cases can anticipate — environment matrices for monorepos, dependency graphs across roots, declared interface contracts between services, agent-domain partitioning for multi-agent sessions. Those need to be designed in the open, not from one shop's experience. The current scope is the floor, not the ceiling.

MIT-licensed. Open source. Install in two commands.

Software manufacturing is becoming a coordination problem between agents. The agents are ready. The context infrastructure is catching up.
